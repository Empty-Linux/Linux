BUG-AUTH-001: Отсутствие rate limiting на отправку SMS

Информация

| Поле | Значение |
|------|----------|
| ID | BUG-AUTH-001 |
| Дата | 2026-01-25 |
| Severity | High |
| Priority | P1 |
| Статус | Fixed ✅ |
| Эндпоинт | POST /api/auth/send-code |

Описание

При отправке SMS-кода отсутствует ограничение на количество запросов. Злоумышленник может отправлять неограниченное количество SMS, что приводит к:
1. Финансовым потерям (SMS платные)
2. Спаму на номер телефона
3. Потенциальной DDoS атаке на SMS Gateway

Шаги воспроизведения

1. Открыть Postman
2. Создать POST запрос на `/api/auth/send-code`
3. В Body указать:
   ```json
   {
     "phone": "+79001234567"
   }
   ```
4. Отправить запрос 10 раз подряд за 1 минуту
5. Все 10 запросов успешны (200 OK)

Ожидаемый результат

После 3-5 запросов за минуту должен возвращаться статус:
Status Code: 429 Too Many Requests
Response:
  ```json
  {
    "success": false,
    "error": {
      "code": "RATE_LIMIT_EXCEEDED",
      "message": "Too many requests. Please try again in 60 seconds",
      "retryAfter": 60
    }
  }
  ```

Фактический результат

Все запросы успешны, SMS отправляются без ограничений.

Доказательство:
```
Request 1: 200 OK - SMS sent
Request 2: 200 OK - SMS sent
Request 3: 200 OK - SMS sent
...
Request 10: 200 OK - SMS sent
```

Окружение

Сервис: Auth Service v1.0
Среда: Staging
Инструмент: Postman v10

Рекомендации по исправлению

1. Добавить rate limiting: максимум 3 SMS в минуту на один номер
2. Добавить rate limiting: максимум 10 SMS в час на один номер
3. Добавить rate limiting по IP: максимум 20 запросов в минуту
4. Возвращать header `Retry-After` при превышении лимита

Исправление

| Дата | Действие |
|------|----------|
| 2025-10-06 | Баг назначен разработчику |
| 2025-10-07 | Исправление в PR #123 |
| 2025-10-08 | Верификация на Staging - OK |
| 2025-10-09 | Деплой в Production |

BUG-AUTH-002: SMS-код возвращается в ответе API (DEV)

Информация

| Поле | Значение |
|------|----------|
| ID | BUG-AUTH-002 |
| Дата | 2025-10-10 |
| Severity | Critical |
| Priority | P1 |
| Статус | Fixed ✅ |
| Эндпоинт | POST /api/auth/send-code |

Описание

В Development окружении SMS-код возвращается в ответе API для удобства тестирования. Однако этот код остался и в Staging сборке, что является критической уязвимостью безопасности.

Шаги воспроизведения

1. Отправить POST запрос на `/api/auth/send-code` (Staging)
2. В Body:
   ```json
   {
     "phone": "+79001234567"
   }
   ```
3. Проверить ответ

Ожидаемый результат

```json
{
  "success": true,
  "message": "Verification code sent",
  "expiresIn": 300
}
```

Код НЕ должен присутствовать в ответе.

Фактический результат

```json
{
  "success": true,
  "message": "Verification code sent",
  "expiresIn": 300,
  "code": "123456"    ← УЯЗВИМОСТЬ!
}
```

Влияние

Критическое:
Любой может авторизоваться под любым номером
Полный обход SMS-верификации
Компрометация всех аккаунтов

Окружение

Среда: Staging (также проверить Production!)
Причина: Отсутствие проверки `NODE_ENV`

Рекомендации по исправлению

1. Удалить поле `code` из ответа во всех окружениях кроме Development
2. Добавить проверку:
   ```javascript
   if (process.env.NODE_ENV !== 'development') {
     delete response.code;
   }
   ```
3. Добавить тест в CI/CD который проверяет отсутствие `code` в ответе

Исправление

| Дата | Действие |
|------|----------|
| 2025-10-10 | Баг обнаружен |
| 2025-10-10 | HOTFIX деплой в тот же день |
| 2025-10-10 | Верификация - OK |

BUG-AUTH-003: Нет блокировки после 5 неверных попыток

Информация

| Поле | Значение |
|------|----------|
| ID | BUG-AUTH-003 |
| Дата | 2025-10-11 |
| Severity | Medium |
| Priority | P2 |
| Статус | Open |
| Эндпоинт | POST /api/auth/verify |

Описание

Отсутствует защита от brute force атаки на SMS-код. Можно бесконечно перебирать 6-значные коды (1 000 000 комбинаций), что позволяет подобрать код за разумное время.

Шаги воспроизведения

1. Отправить SMS-код на номер
2. Отправить 10 запросов на `/api/auth/verify` с неверными кодами:
   ```json
   {"phone": "+79001234567", "code": "000001"}
   {"phone": "+79001234567", "code": "000002"}
   ...
   {"phone": "+79001234567", "code": "000010"}
   ```
3. Все 10 запросов возвращают 401, но без блокировки
4. Можно продолжать перебор

Ожидаемый результат

После 5 неверных попыток:
Временная блокировка номера на 15 минут
Status Code: 429 Too Many Requests
Response:
  ```json
  {
    "success": false,
    "error": {
      "code": "ACCOUNT_TEMPORARILY_LOCKED",
      "message": "Too many failed attempts. Try again in 15 minutes",
      "retryAfter": 900
    }
  }
  ```

Фактический результат

Все запросы возвращают 401 без ограничений:
```json
{
  "success": false,
  "error": {
    "code": "INVALID_CODE",
    "message": "Invalid verification code"
  }
}
```

Влияние

Среднее:
Возможность brute force атаки на 6-значный код
При 10 запросах в секунду: перебор за ~28 часов
Риск компрометации аккаунтов

Рекомендации по исправлению

1. Блокировка после 5 неверных попыток на 15 минут
2. Увеличение времени блокировки при повторных нарушениях
3. Уведомление пользователя о попытках входа
4. Логирование всех неудачных попыток

BUG-AUTH-004: JWT токен не инвалидируется после logout

Информация

| Поле | Значение |
|------|----------|
| ID | BUG-AUTH-004 |
| Дата | 2025-10-12 |
| Severity | Medium |
| Priority | P2 |
| Статус | Fixed ✅ |
| Эндпоинт | POST /api/auth/logout |

Описание

После выполнения logout accessToken продолжает работать до истечения срока действия. Это позволяет использовать украденный токен даже после того, как пользователь вышел из системы.

Шаги воспроизведения

1. Авторизоваться и получить accessToken
2. Сохранить accessToken
3. Выполнить logout:
   ```
   POST /api/auth/logout
   Authorization: Bearer {accessToken}
   ```
4. Получить ответ 200 OK
5. Использовать тот же accessToken для запроса:
   ```
   GET /api/auth/me
   Authorization: Bearer {accessToken}
   ```
6. Запрос успешен (200 OK) — токен всё ещё работает!

Ожидаемый результат

После logout:
Шаг 5 должен возвращать 401 Unauthorized
Токен должен быть инвалидирован

Фактический результат

После logout токен продолжает работать:
```
GET /api/auth/me
Status: 200 OK
Response: { user data }
```

Влияние

Украденный токен работает до истечения (15 минут)
Пользователь не может "выйти" по-настоящему
Риск безопасности при компрометации токена

Рекомендации по исправлению

1. Добавить blacklist токенов в Redis
2. При logout добавлять tokenId в blacklist
3. При каждом запросе проверять blacklist
4. Очищать blacklist по истечении TTL токена

Исправление

Реализован token blacklist в Redis:
```
Key: blacklist:{tokenId}
TTL: равен TTL токена
```
BUG-AUTH-005: Отсутствие валидации формата телефона

Информация

| Поле | Значение |
|------|----------|
|  ID  | BUG-AUTH-005 |
| Дата | 2025-10-13 |
| Severity | Low |
| Priority | P3 |
| Статус | Fixed ✅ |
| Эндпоинт | POST /api/auth/send-code |

Описание

Эндпоинт принимает номера телефонов в разных форматах, что может привести к дубликатам пользователей и проблемам с SMS-отправкой.

Шаги воспроизведения

Все эти запросы успешны:
```json
{"phone": "+79001234567"}     // с +
{"phone": "79001234567"}      // без +
{"phone": "+7 900 123 45 67"} // с пробелами
{"phone": ""+7-900-123-45-67""} // с дефисами
```

Ожидаемый результат

Только формат `+XXXXXXXXXXXX` должен приниматься.
Остальные форматы: 400 Bad Request

Фактический результат

Все форматы принимаются, создаются разные записи в БД.

Влияние

Дубликаты пользователей в БД
Проблемы с поиском пользователя
Путаница при логине

Рекомендации по исправлению

1. Добавить строгую валидацию: `/^\+[0-9]{10,15}$/`
2. Или нормализовать номер перед сохранением
